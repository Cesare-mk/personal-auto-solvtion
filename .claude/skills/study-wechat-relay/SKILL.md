# study-wechat-relay — 学习场景截图答题中继

工具链已经落地，**不要重写、不要自己写轮询循环**。你的职责是：等待 → 读图 → 解题 → 发微信 → 再等待。

```
Ctrl+` 截图 ──► runtime/shots/*.png ─┐
                                     ├─► wait_events.py（阻塞，只报事件名）──► 你识图解题 ──► wechat_gateway.py ──► 微信
微信发消息 ──► runtime/wechat_inbox ─┘                                              ▲                    │
                                                                                    └── 再次阻塞 ◄───────┘
```

先把全文读一遍——这套流程的成败几乎全在纪律上。

## 0. 开工

```bash
# 会话开头确认一次工作目录是项目根即可（Claude Code 默认就在项目根），
# Bash 跨调用会保留 cwd，后面全用相对路径。
cd "$(git rev-parse --show-toplevel)"
```

> 项目换了目录、或用的是解压出来的副本（非 git），把上面那句换成项目根的绝对路径即可。
> 脚本内部不依赖 cwd——配置与运行产物都由 `src/paths.py` 相对**项目根**解析。

**解释器统一写 `scripts/py`**，它转发到装了依赖的那个 Python。
（PATH 上的 `python` 是 Anaconda base，**缺 `mss`/`qrcode`**，截图端和扫码登录会起不来——
所以别图省事直接写 `python`。）

流程靠两个**常驻进程**供血，`wait_events.py` 是第三个（由你自己跑，见 §2）：

| 常驻 | 不在跑的症状 |
|---|---|
| 微信网关（长轮询 + HTTP API `127.0.0.1:8799`）| 永远等不到 `WX` 事件 |
| 截图端（`Ctrl+\`` 截屏 → `runtime/shots/`）| 用户按 Ctrl+` 没反应 |

**先查再起**，`start` 是幂等的（在跑的不动，只补缺的）：

```bash
scripts/py scripts/launcher.py status
scripts/py scripts/launcher.py start
```

> 用户也可能已经用 `scripts\start-all.bat` 起好了。下次进来先 `status` 查一下，在跑就直接进等待。
>
> ⚠️ **别假设常驻进程一定活过了会话中断。** 它们是用 `subprocess.Popen(CREATE_NEW_CONSOLE)`
> 拉起来的，`CREATE_NEW_CONSOLE` 只给新控制台、**不解除父子关系**，会话被拆时可能被一起回收
> （2026-09-16 实测：一次会话中断后网关和截图端**双双消失**，而系统并没有重启）。
> 所以**每次接管中继都先跑一次 `status`**，别凭印象。
>
> 常驻进程现在会写文件日志：`runtime/logs/{wechat_gateway,capture,screenpeer}.log`
> （2MB 滚动 ×3）。进程「莫名其妙没了」时先看这里——未捕获异常、后台线程异常、
> 段错误都会落盘。在此之前日志只存在于各自的控制台窗口里，窗口一关就永久消失。

## 1. 铁律

1. **等待必须阻塞，永远不设短超时。** 它是「等人出题」的，安静是正常的，不是卡死。
2. **同一张图/同一条消息只处理一次。** 账本保证不重复打印；你也不要去重读旧图。
3. **题号以图为准。** 图里写「第 3 题」就回「第 3 题」，不要重排编号；一图多题就逐题分开回。
4. **算法题必须先跑通样例再发。** 没验证过的代码不许发微信。
5. **算法题发「思路文字 + 代码图」两条，不发源码文件。** 代码图发不出去才退化成代码片段。
6. **一轮处理完立刻回到阻塞等待**，不要在两次等待之间插 `sleep` 或短超时试探。
7. **不要做 LLM 路由**：双向消息由你处理，脚本只负责搬运。
8. **图是唯一信息源**：整图读一遍就够，**不裁剪、不放大、不重复读、不搜原题**——
   搜来的题可能跟图不符，反而答错（除非用户明说「搜一下」）。

## 2. SOP（每一轮走这五步）

### 步骤 1 — 阻塞等待

```
1) Bash({ command: "scripts/py src/wait_events.py", run_in_background: true })  → 拿到 task_id
2) 反复 TaskOutput(task_id, block: true, timeout: 600000)
     · status: running    → 继续调，这正常，不是失败
     · status: completed  → 取输出，进入步骤 2
3) 整轮期间：不要 TaskStop、不要因为等太久重开、不要改用 --once 反复问
```

`TaskOutput` 的 timeout 上限是 10 分钟，到点返回 `running` 属正常，接着调下一次即可。

**空闲退出的准确语义**（误解它会导致你误判「卡死」）：
`--idle-timeout` 默认 10s，但**计时从打印出第一个事件之后才开始**。
一个事件都没打印过时它**永远不退出**——屏幕上只有横幅、什么都没有，这是完全正常的，
不要重开、不要加超时、不要改成 `--once` 去轮询试探。

万一被超时杀掉，**直接再跑一次**就行：账本保证已打印的不重复打印，
而被杀那轮**已打印但你没看到**的，会以 `REPLAY` 补给你（见 §3）。

想看单轮快照（调试/自测）才用 `scripts/py src/wait_events.py --once`。

**单实例锁（会被拒绝启动，别慌）**：`wait_events.py` 启动时会取一把 PID 锁
（`runtime/state/wait_events.lock`）。已经有实例在跑时它**拒绝启动、退出码 3**，
并打印占用者的 PID / 启动时间 / 命令行。这是**故意的**——两个实例并存时，
旧实例会把事件消费掉、输出却打进一个已经消失的控制台，事件看起来凭空消失，
事后连 `REPLAY` 都补不回来。看到这个报错时：

- 确认那个实例确实不该在跑（比如是上个会话的遗留）→ 加 `--takeover` 接管，它会杀掉旧的；
- 只是想看看 → `scripts/py src/wait_events.py --status`（诊断模式不取锁，不会被挡）。


### 步骤 2 — 读图 / 读消息

- `IMG <绝对路径>` → 用 **`Read`** 工具读那张图。
- `WX <正文>` → 用户从微信发来的话；带 `[图片]/[文件]` 时后面就是本地路径，同样 `Read`。

**一次到位**：整图读一遍，题面/样例/语言/模式全在里面。

**图被截断时**：若题面明显不完整，而本轮还有后续 `IMG`，就接着读下一张（多半是同一题的后半）；
后面没有新图了就用手上这张直接做，不要干等。

判题：先判题型（单选/多选/不定项/判断/填空/简答/算法），
**抄下题号原文**（「3.」「第 3 题」「(3)」都算）。算法题另外记下：

- 题目描述、输入输出格式、**全部样例**、数据范围
- **要求语言**（图片里代码模板的语言，没有就用 **Java** 并说明）
- **模式**：`ACM`（完整程序读 stdin 写 stdout）还是 `核心代码`（只交类/函数，LeetCode 风格）

### 步骤 3 — 解题与**本地验证**

产物落盘，每题一个批次目录：

```bash
B="runtime/work/$(date +%Y%m%d_%H%M%S)" && mkdir -p "$B" && echo "$B"
# 记下打印出来的 $B；它同样不跨 bash 调用保留，后续命令要重新赋值。
```

**算法题**：

- Java 的硬约束（不遵守 javac 直接报错）：文件名必须是 `Solution.java`，
  类名必须是 `public class Solution`（大小写必须一致），ACM 模式还要有
  `public static void main(String[] args)`。
- ACM 模式把样例输入存 `$B/t1.in`，真的跑一遍：
  - Java：`javac -encoding UTF-8 -d $B $B/Solution.java && java -cp $B Solution < $B/t1.in`
  - Python：`scripts/py $B/solution.py < $B/t1.in`
  - C++：`g++ -O2 -o $B/a $B/solution.cpp && $B/a < $B/t1.in`
- 核心代码模式：写 `$B/run_tests.py` 直接调用你的函数/类，断言所有样例。
- **全部样例通过才继续**；不过就改，改完再跑（最多绕 3 轮，仍不过就如实告诉用户卡在哪）。

**非算法题**：在脑子里核对选项/空；不确定的，把依据写清楚。

### 步骤 4 — 发到微信

```bash
# 非算法题
scripts/py src/wechat_gateway.py send --text "第 3 题（单选）｜答案：B
简析：……"

# 算法题（思路文字 → 代码图，两条）
scripts/py src/code_image.py --in $B/Solution.java --out $B/code.png \
    --lang java --title "T1 · 两数之和" --subtitle "Java · 核心代码模式" \
    --footer "时间 O(n) / 空间 O(1)" --highlight 5,6
scripts/py src/wechat_gateway.py send \
    --text "题目：两数之和｜模式：核心代码｜语言：Java
思路：哈希表边遍历边记下标……
复杂度：时间 O(n)，空间 O(n)
样例：2/2 通过" \
    --image $B/code.png
```

成功判定：输出 `[结果] 成功 …`（退出码 0）。失败见 §5。

### 步骤 5 — 回到步骤 1

本轮还有没处理完的事件（一次等待可能返回多张图/多条消息）就先处理完，
然后**立刻**再次进入步骤 1。不要问用户「还要继续吗」，不要打印总结就停下。

## 3. 事件格式

```
IMG ...\runtime\shots\20260916_120705_542.png          # 新截图（绝对路径）
IMG ...\runtime\shots\20260916_115900_777.png REPLAY   # 上一轮被中断，补打的
WX 帮我看看这题                                        # 微信消息：只有用户说的话
WX 这题用 Python 再写一遍 [图片] ...\wechat_media\a.jpg # 带附件时给本地路径
WX 在吗 [chat=xxx@im.wechat]                           # 只有非默认会话才带 chat
WX 在吗 REPLAY
```

- **`REPLAY`** = 上一轮脚本被强杀、这些已打印但没能确认送达。**照常处理**，同样要回复用户。
- `WX` 行默认只给用户说的话（无时间/msg_id 噪音）。只有出现 `[chat=…]` 时才需要用
  `--to <chat_id>` 指定回复目标，否则直接回默认会话。
- 用户连续发多条时可能一次出现多条 `WX`，**合并理解后再回一条完整答案**。
- 需要完整 JSON（调试）时加 `--wechat-meta`。

## 4. 回复模板

**非算法题**（题号必须与图片一致，答案先行）：

```
第 3 题（单选）｜答案：B
简析：……

第 5 题（多选）｜答案：ABD
简析：……

第 7 题（填空）｜答案：(1) 3  (2) 5
简析：……

第 9 题（判断）｜答案：错误
简析：……
```

- **简析要短，直击要点。** 一图多题可以合并成一条（按题号分行）或一题一条，但顺序按题号。
- 一图只有一题时别加多余前缀。

**算法题**（两条，顺序固定）：

1. 文本：题目名 + 模式（ACM/核心代码）+ 语言 + 3~6 行思路 + 复杂度 + 样例验证结论
2. 代码图：`code_image.py` 渲染（深色、带行号、标题写题号，页脚写复杂度）

> **不发源码文件**（用户明确要求只看代码截图）。`--file` 参数还在，别用就行；
> `Solution.java` 只作为本地跑样例的载体落在 `$B/` 下。

二级降级——代码图发不出去时，退化成代码片段（网关按代码块边界切片，不会把围栏切成两半）：

```bash
scripts/py src/wechat_gateway.py send --text "…思路…

\`\`\`java
<完整代码>
\`\`\`"
```

## 5. 异常处理

| 现象 | 处理 |
|---|---|
| `send` 报 **prepare failed / 会话尚未建立** | ⚠️ 这个报错**指向不可靠**：限流、会话过期、服务端抖动都会套用同一句话。别急着让用户去发消息——**先按 10~30s 间隔重试 3~5 次**，多数会自愈（实测第 6 次成功）。仍不行再让用户给机器人发一条消息 |
| `send` 报 **ret=-2（频率限制）** | 等 10~30s 再发；长内容合并成一条，别连发多条 |
| 想知道 `send` 到底卡在哪 | **`send` 不依赖常驻网关**（进程内直连 iLink，2026-09-16 核实）。所以「发不出去」和「网关死没死」是两件独立的事，别混为一谈：网关挂了照发不误，发不出去也未必是网关的锅 |
| `send` 报 **HTTP 4xx / 网络错误** | `scripts/py src/wechat_gateway.py doctor`；token 失效就 `login --new` 重新扫码（**二维码必须用户本人扫**，你扫不了）|
| 用户说「这是别人的包 / 我要用自己的微信」 | `scripts/py src/wechat_gateway.py login --new` 申请全新二维码，扫完就是他自己的机器人；不加 `--new` 会沿用包里原有的身份 |
| 图片发出去是**灰块** | `aes_key` 参数被改坏了。别自己改协议，恢复 `src/ilink_client.py` 后重发 |
| `wait_events` 一直没输出 | **正常**，零事件时它就是要一直阻塞。确认网关活着（`/health` 的 `count`）和截图端在跑即可；**不要**改短超时、不要重开 |
| 图片读不出来（坏文件/半截） | 跳过它处理其余事件，并回一条「这张图读取失败，麻烦重截」 |
| 截图里**没有题目**（截到桌面/聊天窗）| 回一条「没识别到题目，请把题面放到屏幕可见处再按一次」，然后**立刻回去等待**，不要假装答过 |
| 用户在微信里发的是**纯聊天/催问** | 直接回，不走解题流程；同时继续等待 |
| 网关 / 截图端挂了 | **先看 `runtime/logs/` 下对应的 .log**（未捕获异常、后台线程异常、段错误都在里面）→ 再 `scripts/py scripts/launcher.py start` 拉起。收件箱是追加写，重启不丢消息 |
| `wait_events` 报「已有一个在跑，拒绝启动」（退出码 3） | 正常保护。确认是上个会话的遗留就 `--takeover`；只想看状态用 `--status` |
| 用户按了 Ctrl+` 但没出图 | 看 `runtime/logs/screenpeer.log`：`触发截屏` 说明热键命中了（问题在发送/落盘）；**`触发被节流跳过`** 说明两次按键间隔小于 `cooldown`（默认 2s），被有意丢弃了 |
| 起不来 / 端口被占 / 改了配置不生效 | 看 `README.md` 的「出问题怎么办」和 `docs/ADAPTATION.md` |

需要长时间思考时，可以先 `scripts/py src/wechat_gateway.py typing --status start`
让微信端显示「正在输入…」，发完再 `--status stop`（可选，默认发送时自动带）。

## 6. 省上下文的纪律

- 只读**本次新打印**的图；`Read` 一张就够，不要重复读、不要读 `runtime/shots/` 里的历史图。
- 长代码/长推导**落盘到 `$B/`**，对话里只留结论（要发的内容 + 必要的 2~3 行理由）。
- 发完就忘：不要把发过的内容再复述一遍，直接回到等待。
- 一次等待返回多个事件时**按顺序处理**，不要把多张图的推理混在一起。
